# v5 Decisions log

Locked decisions live in `MASTER-PLAN.md` §2 and §10. This file records every call an agent had to make on its own.
Format: `- **D-##** (M#, role) DEFAULTED — <decision>. Why: <reason>. Overrule: <what changes if Kevin disagrees>.`

- **D-01** (M0, orchestrator) DEFAULTED — The v4 harness (text parity against Figma, v4 click-throughs, Figma-ref diffs) is archived to `scripts/v4/` and no longer runs. v5's `npm run check` = v5 click-throughs (Test-flows entries + cross-persona sync) + visual regression against code-rendered baselines in `ref/v5/` + style hygiene + a no-"%"-in-money lint. Why: v5 is code-first, there is no Figma token, and v4 assertions describe retired behaviour. Overrule: re-port parity once v5 frames exist in Figma.
- **D-02** (M0, orchestrator) DEFAULTED — The v4 screens are unregistered in M0, so between M0 and M1 the app boots to a v5 index/placeholder screen. v4 stays intact on `main`. Why: v5 replaces the state model the v4 screens depend on. Overrule: none needed — v4 is reachable from `main`.
- **D-03** (M0, spec writer) DEFAULTED — Money is stored and computed in integer cents (`js/money.js`); breakdown, receipt and payout rows print exact cents ("$16.00"), price lists / list-row estimates / the rush ladder print whole dollars when whole ("$25"); negatives use U+2212 ("Taily fee −$12.50"). Why: 10 % of a $45 service is $4.50, so cents are unavoidable; one rule per surface keeps columns aligned. Overrule: change `fmt` / `fmtExact` in `js/money.js`.
- **D-04** (M0, spec writer) DEFAULTED — The courier charge never appears on the tailor's side (no row in the tailor breakdown, not part of payout); the courier's 10 % markup is Taily revenue. Why: the customer pays it and it goes to the courier + Taily; showing it to the tailor would inflate "order total". Overrule: add a muted "Courier (paid by customer)" row to `tailorBreakdown`.
- **D-05** (M0, spec writer) DEFAULTED — When a customer cancels within 24 h, the kept deposit is paid to the tailor in full, with no Taily fee taken. Why: the doc says the deposit "covers the non-refundable home-visit fee", which is the tailor's. Overrule: route the kept deposit (or part of it) to Taily in `cancelTerms`.
- **D-06** (M0, spec writer) DEFAULTED — On a customer no-show the deposit is kept and the tailor is paid the larger of the deposit and the $25 no-show compensation (`noShowPayout = max(deposit, $25)`). Why: keeps v4's $25 guarantee without paying twice when the deposit already exceeds it. Overrule: pay deposit + $25, or a flat $25.
- **D-07** (M0, spec writer) DEFAULTED — "Try again ×2" = up to three attempts in total; the tailor is hidden from the list for that job only when the request expires with both retries used (the second Try again also expired). Why: reconciles §2 "Try again ×2 then other tailors" with §10 "after the 2nd expiry"; C7 lists Try again 1/2 and 2/2 as distinct states. Overrule: hide after the second expiry (one fewer attempt) by setting `MAX_RETRIES: 1` and relabelling.
- **D-08** (M0, spec writer) DEFAULTED — A tailor who declined a job stays in "Tailors near you" for that same job as a dimmed row with the note "Declined this job" and cannot be booked for it; any other job can book them normally. Why: the doc allows re-requesting "for a different job"; with a one-tailor seed, hiding the row would make the declined state indistinguishable from "no tailors". Overrule: hide declined tailors for that job.
- **D-09** (M0, spec writer) DEFAULTED — The prototype runs on a frozen demo clock (Tue, Oct 13, 2026 · 10:00 AM, `state.clock`); countdowns, the 24 h window and expiries move only when a Test-flows step or a transition moves the clock — nothing ticks in real time. Why: deterministic screenshots and click-throughs; every timer state stays reachable from the menu. Overrule: add a 1-minute interval that calls `advanceClock(1)` outside `?test=1`.
- **D-10** (M0, spec writer) DEFAULTED — Visual baselines are one per Test-flows key (`ref/v5/<key>.png`), not one per screen id. "Sibling" now means "gets its own Figma frame at sync"; in code every state is the same screen file reached by its flow key (no extra registered routes). Why: covers every state (overlays included) with one mechanism and keeps one file per layout. Overrule: register sibling ids and baseline by id.
- **D-11** (M0, spec writer) DEFAULTED — A job holds at most 10 garments (`MAX_ITEMS`). Why: C1 lists a "max items" state without a number; 10 fits one home visit and the tile grid. Overrule: change `MAX_ITEMS` in `js/data.js`.
- **D-12** (M0, spec writer) DEFAULTED — Reschedule is available only more than 24 h before the visit; the customer picks another open slot of the same tailor and the booking stays Confirmed immediately (the tailor is notified, no re-approval). Within 24 h the customer can message or cancel. Why: open slots are the tailor's own availability, and a re-approval loop would duplicate the request flow. Overrule: send reschedules back through `requested`.
- **D-13** (M0, spec writer) DEFAULTED — The machine screen inventory lives in `js/inventory.js` (importable by the browser index screen and by Node), not `scripts/screens.json`, which is archived with the v4 harness. Why: `sys-index` and the harness both need it without a fetch. Overrule: generate a JSON copy for tools that need one.
- **D-14** (M0, spec writer) DEFAULTED — A suggested time has no expiry; the deposit hold stays authorized until the customer accepts (captured) or picks another tailor (released). Why: the doc gives no window and the customer is the one who must act. Overrule: add `SUGGESTION_EXPIRY_H` to `POLICY`.
- **D-15** (M0, spec writer) DEFAULTED — An expiry releases the deposit hold; Try again re-authorizes the same amount on the same card. Why: §2 says expired → hold released in full. Overrule: keep the hold through retries.
- **D-16** (M0, spec writer) DEFAULTED — The Taily fee and the deposit are rounded half-up to the cent once per order, not per line. Why: the tailor sees one fee row per job. Overrule: per-line rounding in `money.js`.
- **D-17** (M0, spec writer) DEFAULTED — Visits are 30 min at the shop and 60 min at home, start on :00 / :30 between 9 AM and 9 PM, and the earliest bookable slot is 3 h from now (`MIN_LEAD_H`) so the 2 h reply window ends before the visit. Why: needed to generate open slots; not in the doc. Overrule: edit `VISIT_MINUTES` / `POLICY.MIN_LEAD_H`.
- **D-18** (M0, spec writer) DEFAULTED — A visit must be at least one calendar day before the need-by date; slots on or after the need-by are not offered ("nothing open before need-by" when none remain), and a need-by before tomorrow is a field error. Why: the tailor needs the garment after the fitting; the rush ladder starts at "≤1 day". Overrule: allow same-day (treat as the 1-day rush tier).
- **D-19** (M0, spec writer) DEFAULTED — "At the shop" lists shop-enabled tailors within 5 miles of the customer's zip (mock `ZIP_INFO` distances); home visits use only the tailor's zip list. Why: the doc filters home visits by zip but says nothing for shop visits. Overrule: change `SHOP_RADIUS_MI`.
- **D-20** (M0, spec writer) DEFAULTED — Tailor onboarding Test-flows steps reset the seed tailor to a blank profile with the same id (`amara`), so what the tailor enters is what Sarah sees in the list. Why: one-tailor seed and the cross-persona demo. Overrule: onboard a second, separate tailor.
- **D-21** (M0, spec writer) DEFAULTED — `state.persona` is `'customer' | 'tailor'` (v4 used `'user'`); `sys-*` screens keep the current persona. Why: matches the v5 docs' vocabulary. Overrule: none needed.
- **D-22** (M0, spec writer) DEFAULTED — The customer can withdraw a pending (or suggested-time) request from the request screen; the hold is released in full and the job returns to the list. Why: C6 has no exit otherwise for a 2 h wait. Overrule: remove the Withdraw action.
- **D-23** (M0, spec writer) DEFAULTED — After a price change the deposit stays as captured; the balance is the new total minus the deposit, and if the new total is below the deposit the difference is refunded at Ready. Why: §2 fixes the deposit; a large removal could otherwise make the balance negative. Overrule: recompute the deposit.
- **D-24** (M0, spec writer) DEFAULTED — A tailor's payout is created as pending when the job is marked Completed and is paid out weekly (the following Friday); kept deposits and no-show pay follow the same schedule. Why: T8 needs pending / paid / failed states and the doc gives no timing. Overrule: pay on completion.
- **D-25** (M0, model worker) DEFAULTED — The price is fixed when the request is sent: rescheduling or accepting a suggested time keeps the booked quote, even if the new visit date would fall in a higher rush tier. Why: the customer agreed (and the deposit was held) on that total; only the tailor's post-fitting price change moves it. Overrule: recompute `rush` from the new slot in `rescheduleBooking` / `acceptSuggestion`.
- **D-26** (M0, model worker) DEFAULTED — `approvePriceChange` also works after the customer has messaged the tailor (`priceChange.state === 'messaged'`); `messageAboutPriceChange` works once. Why: §2 says disputes settle in chat, so the customer must still be able to approve afterwards. Overrule: require `pending` for approve.
- **D-27** (M0, model worker) DEFAULTED — A tailor who is not fully onboarded (any of the six flags false) is treated like an out-of-area tailor in `eligible` / `tailorsFor` (reason `zip` for home visits, `shop-off` for shop visits). Why: D-20 resets the seed tailor to blank during onboarding and the list must then be empty without a new empty-state kind. Overrule: add a `not-bookable` empty state.
- **D-28** (M0, model worker) DEFAULTED — `openSlots` / `nextOpening` return ISO start strings (`'2026-10-15T17:00'`), not objects; the end is `start + VISIT_MINUTES[visitType]`. `money.estimate(tailor, job, slotIso)` reads the rush tier from the slot it is given (null → no rush); `state.estimateNext(tailor, job)` passes the tailor's next opening. Why: keeps `money.js` free of state and matches the `slotStart` arguments of the transitions. Overrule: return `{ start, end }` objects.
- **D-29** (M0, component builder) DEFAULTED — `customerBreakdown` copy the spec left open: the estimate stage labels the total "Estimated total" (later stages "Total"); the Balance status reads "Due when ready" until Ready, "Due now" at the Ready stage, "Paid" after; the Services row carries the caption "<Tailor>’s prices" when `tailorFirst` is passed; a refund row ("Refund to your card") appears at Ready / Paid when `quote.refund > 0` (D-23). Why: C-stage screens need a distinct word for money that is due right now, and a refund must be visible where the balance would have been. Overrule: edit the `customerBreakdown` row table in `js/components.js`.
- **D-30** (M0 review fixer) DEFAULTED — `customerBreakdown` takes the deposit word from the appointment, not the stage: `depositState` (`authorized` "On hold" · `captured` "Paid" · `released` "Released" · `refunded` "Refunded" · `kept` "Kept"). A pending request is a hold that decline / expiry / withdraw can release (§2: authorized at request, captured on accept), so c-request and c-pay pass `appt.payments.deposit.state`. Without `depositState` the old stage words stay (estimate "Due today", later stages "Paid"). Why: "Paid" on a pending request contradicted "held, not charged". Overrule: edit `DEPOSIT_STATUS` in `js/components.js`.
- **D-31** (M0 review fixer) DEFAULTED — `tryAgain` re-checks the slot is still open (`slot-unavailable`) before re-authorizing, and `openSlots` builds each start from wall-clock fields (`setHours`) so a daylight-saving changeover day keeps its hours. The visual gate is 0.10 % of pixels AND at most 2000 mismatching pixels (`MAX_PX` in `scripts/v5/diff.mjs`). A missing `runFlow` or an empty registry now fails flows and visual (`--allow-empty` for a scratch run). Why: review findings R0-02, R0-03, R0-04, R0-08. Overrule: change the guard / constant.
- **D-32** (M0, Figma sync) DEFAULTED — Figma node ids for v5 live in a new `scripts/screens.json` holding only a `v5` key (`pages`, `boards`, `components`, `screens`); the v4 file stays archived at `scripts/v4/screens.json` and the screen inventory stays in `js/inventory.js` (D-13). The v5 masters are prefixed `v5 / …` in a new Components section "V5 — M0", built with variants for visual states (not Fee-Row-style variable modes) and text overrides for content; `chatBubble` nests the existing T2 / Chat Bubble, `emptyState` / `readOnlyBanner` nest CTA, review / chat photos nest Photo. Overrule: move the map into `js/inventory.js`, or convert content states to variable modes.
